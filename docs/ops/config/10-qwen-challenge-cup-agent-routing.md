# 10 · 挑战杯 Qwen Agent 路由

> **状态：建议方案，尚未生效。** 本文用于后续模型接入与 PPT 汇报；不修改任何 Agent、Profile、Provider 或密钥。
>
> **快照日期：2026-08-26。** 模型可用性、价格和日期快照 ID 必须在真正接入当天复核；正式运行只能使用钉选版本，不能写 `latest`。

## 结论

挑战杯不应让十个角色都使用同一档模型。高频且可回滚的协调、检索和版本核对使用 `qwen3.7-flash`；需要准确处理证据关系、长上下文和结构化产物的日常工作使用 `qwen3.7-plus`；只把 `qwen3.8-max` 留给少量高影响的独立评审和晋级决策。

这里的“能力档位”是任务所需的推理与判断能力，不是人的 IQ，也不是厂商公开的参数量。DashScope 托管模型未公开可供本项目核验的参数量，不能用“多少 B 参数”替代真实的任务验收。相对成本仅表示同一账户下的产品层级；实际单价以接入当天 DashScope 价格页和账户区域为准。

## 模型层级与适用边界

| 模型 | 已知能力摘要 | 适合承担 | 不应默认承担 |
| --- | --- | --- | --- |
| `qwen3.7-flash` | 1M 上下文、最大输出 64K，支持工具与结构化输出 | 高频协调、检索计划、版本摘要 | 独立科学裁决、复杂证据冲突的最终判断 |
| `qwen3.7-plus` | 1M 上下文、最大输出 64K，支持工具与结构化输出 | 证据提炼、知识关系、受控执行、日常修订 | 每一轮最终晋级裁决 |
| `qwen3.8-max` | 1M 上下文、最大输出 64K，支持思考、工具与结构化输出 | 独立评估、关键修订、不可逆或高成本决策 | 批量检索、常规格式转换、逐条入库 |
| `qwen3-coder-plus` | 1M 上下文，面向代码与脚本任务 | 执行阶段的代码/脚本诊断辅助 | 替代证据评审或正式研究结论 |
| `qwen3.6-plus` | 1M 上下文、最大输出 64K | 已完成本机最小调用验证的稳定回退 | 把“已接通”误表述为十角色路由已完成 |
| `qwen-long` | 10M 上下文；不支持思考和 Function Calling | 超长论文、日志或材料的分段压缩 | 需要工具编排、严格推理或正式裁决的节点 |

扫描论文、表格或实验图时，应在后续单独验收 `qwen3.5-ocr` 或 `qwen3-vl-*`；图像、语音、全模态、翻译和向量模型各有不同输入协议，不能直接替代当前文本 Agent 的对话模型。

## 每个角色为什么这样选

### 科研协调：用 Flash，把预算留给真正的判断

协调的输出是任务分派、状态汇总和结构化交接。它可以引用下游的证据定位，不应该自己制造科学结论；因此优先追求低延迟和高并发。遇到冲突材料时升级到 Plus，而不是让 Flash 强行“拍板”。

### 搜索 Agent：用 Flash，因为来源而不是模型才是事实锚点

搜索的价值是把知识缺口变成检索式，并登记命中与未命中来源。来源链接、时间和相关性可以复查，故高频工作使用低成本 Flash 最划算。跨学科或极窄主题的检索规划才值得临时使用 Plus。

### 提炼 Agent：用 Plus，避免丢掉限定条件和反证

提炼要区分研究对象、条件、指标、限制和反例。它不是普通摘要任务；只省一次模型费用而漏掉一个反证，会让后续实验和评估付出更大代价。Plus 是该类高频精细阅读任务的成本—质量平衡点。

### 知识管理 Agent：用 Plus，重视关系正确而不是文笔

知识管理要维护 evidence lineage、作用域和候选提升边界。它需要理解“两个说法是否可合并”“同一结论在什么条件下失效”，比检索更吃推理质量；但此类日常治理数量多，默认 Max 不经济。

### 资料入库：用 Plus，保证可复用而非只保证能存进去

资料入库必须在清洗和分类后保住来源字段、元数据和证据定位。Plus 能更稳地处理格式不整齐的材料；若原始材料本身是扫描件或图表，应该换 OCR/VL 流程，而不是让文本模型猜内容。

### 执行 Agent：用 Plus，Coder 只做技术辅助

执行 Agent 的关键是遵循已冻结协议、正确调用受控工具并登记不可变产物。Plus 适合工具编排与严格结构化输出。`qwen3-coder-plus` 可帮助定位脚本错误，但其诊断文本不能代替正式运行回执、实验结果或研究结论。

### 实验修订 Agent：日常 Plus，关键改向升 Max

假说和协议通常需要多次可回滚的修改，默认 Plus 能避免成本随轮次膨胀。只有修订会改变研究方向、资源投入或正式候选资格时，才让 Max 做高质量的反事实和风险检查。

### 评估 Agent：用 Max，购买的是发现错误的概率

评估角色不应复述上游结论，而要独立检查指标、反证、稳健性和主张边界。它的调用量应很少，但单次失败代价最高，所以 Max 的相对高价最有理由放在这里。独立评估仍需来源引用、评分量表和人工关口，不能只因为模型更强就自动批准。

### 迭代决策：日常 Plus，晋级或淘汰升 Max

一般轮次只是在候选间排序、安排补证和分配预算，Plus 的综合质量足以胜任。决定晋级、淘汰、停止或显著改预算时，错误会放大到后续整条链路，应升级 Max 并保留决策理由。

### 版本治理：用 Flash，让机器规则而非模型决定边界

版本治理以 manifest、hash、冻结状态和授权记录为准。Flash 负责将差异解释成人可读的报告；它不拥有更改版本或绕过门禁的权限。因而高价模型在这里几乎没有边际收益。

## 接入前的硬性门槛

当前活跃 Operator 配置中，DashScope Provider 已通过 `dashscope_main/qwen3.6-plus` 完成最小真实调用验证；本文推荐的 `qwen3.7-*`、`qwen3.8-max` 和 `qwen3-coder-plus` 尚未注册为 Vibelution 模型/Profile，也没有绑定到上述十个角色。当前十个挑战杯角色仍绑定 `opencode_go/deepseek-v4-flash`。

真正接入时按以下顺序执行：

1. 在 DashScope 账户中确认当天可用的**日期快照 ID**与价格，登记 Provider 模型目录和 Profile；密钥只保留为 `env:DASHSCOPE_API_KEY`。
2. 分别验证结构化输出、Function Calling、调用回执、超时/重试与 prompt cache；厂商“支持工具”不等于本项目协议已兼容。
3. 先以小样本做角色对照：质量（证据完整/错误率）、时延、token 成本、工具成功率；通过后再逐角色切换。
4. 正式挑战杯运行继续受 `CatalogRunAuthorization`、结构化输出和调用回执约束。模型路由建议、开发 fixture 和连通性测试都不是正式科研结果或人工批准。

配置字段与接入方法见 [03 · 模型钉选与 Profile](./03-llm-model-and-profile.md)、[05 · 厂商菜谱](./05-llm-vendor-recipes.md) 和 [09 · Agent 配置自检清单](./09-agent-checklist.md)。
