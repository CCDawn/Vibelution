# 设置工作台一页快速配置设计

**Status:** approved-design
**Date:** 2026-07-12
**Owner:** web-workbench-surface
**Target:** `/config`
**Version impact:** patch

## 1. 目标

把设置页从“同时展示设置索引、Provider 列表、Provider 详情、四步向导和底部编辑操作”的高噪声页面，调整为以完成配置为首要目标的桌面工作台。

用户配置模型连接时只需：

1. 选择服务商；
2. 输入 API Key；
3. 点击“检测并生成配置”；
4. 检查系统生成的配置预览并点击“确认并保存”。

系统负责自动带入端点、协议与驱动，测试连接，发现模型，并给出可解释的默认模型推荐。正式写入仍需要用户最后确认。

## 2. 用户和使用场景

- 目标用户：需要完成 Vibelution 初始配置或新增模型连接的本地用户，不要求理解 Provider、wire protocol、模型目录和环境变量细节。
- 主要任务：以最少输入完成一个可用模型连接。
- 次要任务：查看和维护已有 Provider、替换凭据、修改路由、重新发现模型、固定或取消固定模型。
- 产品语气：紧凑、平静、可扫描的桌面运维工作台，不采用营销页式大卡片或装饰性留白。

## 3. 范围

### 3.1 本轮包含

- 重整设置页整体骨架、左侧分区导航、页面头部、状态摘要和内容容器。
- 新增“一页快速配置”作为模型连接的默认入口。
- 把已有 Provider 管理移到同一分区的次级入口。
- 把高级端点、协议和兼容参数放入默认收起的高级区。
- 将现有四步 Provider 向导收敛为输入、自动检测、确认保存三个 UI 阶段。
- 覆盖加载、检测、部分失败、认证失败、无可推荐模型、保存失败和成功状态。

### 3.2 明确不做

- 不设计手机端或触屏专用布局。
- 不改变其他路由、Agent 的模型选择入口或 Launcher 启动设置。
- 不引入新的 Provider、模型或凭据事实源。
- 不在路由中直接引入 `@heroui/react`。
- 不改变 operator config 的真实路径和所有权。
- 不自动保存、自动覆盖正式配置或未经确认固定模型。

## 4. 现状问题

当前设置页在一个连续页面中同时展示：

- 过窄且信息密度失衡的设置分区索引；
- 占据大面积高度的 Provider 列表；
- 当前 Provider 的连接、模型、协议和诊断详情；
- 长期展开的四步 Provider 向导；
- 页面底部固定的编辑状态和操作条。

这些区域都在争夺主视觉，导致用户无法快速判断“当前是否可用、还缺什么、下一步做什么”。大量 Provider 行、模板按钮和空白区域进一步削弱了扫描效率。

## 5. 信息架构

设置页保留固定左侧分区导航，主内容区顶部使用紧凑标题与配置状态。模型分区提供三个入口：

1. **快速配置**：默认入口，只呈现必要输入、自动处理结果和最终确认。
2. **管理已有连接**：承载 Provider 列表、详情、凭据替换、路由修改、模型管理和诊断。
3. **高级设置**：承载手动端点、协议、兼容模式、本地部署等低频参数。

快速配置与 Provider 管理不能同时纵向堆叠。用户切换入口时，主内容区只呈现一个工作上下文。

## 6. 快速配置布局

桌面主内容区使用左右双栏：

- 左栏：服务商选择、API Key、默认收起的高级参数，以及“检测并生成配置”主操作。
- 右栏：稳定尺寸的自动处理结果、推荐模型、风险说明，以及最终保存操作。

页面底部不再使用覆盖内容的全局浮动操作条。保存操作位于当前工作面板内部，并与其影响的配置对象保持邻近。

左侧设置导航保持固定宽度；模型快速配置在 1280 像素宽度下仍维持双栏。更窄的桌面窗口可出现内容区内部滚动，但本轮不定义移动端重排契约。

## 7. 交互流程

### 7.1 输入阶段

首屏只有两个必填项：

- 服务商模板；
- API Key（`auth_kind=none` 时不显示）。

服务端点、驱动、协议和兼容参数由模板自动带入。中转、私有部署和自定义 Provider 可展开高级区覆盖默认值。

### 7.2 自动检测阶段

点击“检测并生成配置”后，右栏依次显示：

1. 识别端点和 Provider 身份；
2. 测试凭据和连接；
3. 发现可用模型；
4. 生成默认模型推荐。

检测只生成临时预览，不应用正式配置。检测状态必须保留稳定几何，避免结果加载导致页面跳动。

### 7.3 确认阶段

结果区展示：

- 识别出的端点、协议和驱动；
- 发现模型数量；
- 推荐模型和推荐理由；
- 可更换的候选模型；
- 保存会影响的 Provider、凭据引用和固定模型。

用户点击“确认并保存”后，`ConfigRoute` 在一次用户操作内串联现有 Provider draft、凭据、模型固定和配置应用路径。正式 operator config 只在所有前置草稿步骤成功后应用。

## 8. 组件边界

| 模块 | 职责 |
| --- | --- |
| `ConfigRoute` | 配置查询、草稿状态、API 调用、busy/error 状态、最终应用和 React Query 收敛。 |
| `ConfigQuickSetupPanel` | 快速配置的输入、检测进度、预览和确认界面；只拥有本次页面会话的展示状态。 |
| `ConfigProviderRegistryPanel` | 已有 Provider 的列表、详情、凭据替换、路由、模型和诊断维护。 |
| `configProviderLogic.ts` | Provider draft 构造、自动补全、可解释模型推荐和阶段转换的纯函数。 |
| VUI/HeroUI | 按钮、输入、选择、状态、折叠区和焦点行为；不拥有配置事实。 |

`ConfigQuickSetupPanel` 不直接调用 API，不写 React Query cache，也不写 operator config。它只通过 typed callbacks 把用户意图交给 `ConfigRoute`。

## 10. 推荐模型规则

模型推荐必须是确定、可测试和可解释的纯规则，不使用 LLM：

1. 排除 disabled 或协议不兼容的模型；
2. 优先使用 Provider 模板声明的默认模型；
3. 否则优先选择已验证可用且能力信息完整的模型；
4. 仍存在多个候选时使用稳定排序，并在 UI 中允许用户更换；
5. 没有安全候选时不自动推荐，要求用户手动选择或输入模型。

## 11. 状态、错误和恢复

- **Idle**：解释只需两个必填项，展示系统会自动完成的内容。
- **Checking**：显示每个自动阶段的进行中、成功或失败状态，禁用重复提交。
- **Auth failed**：定位到 API Key，保留非敏感输入，允许原地重试。
- **Endpoint failed**：定位到端点或协议，自动展开高级区供用户修改。
- **Discovery unavailable**：标记为降级状态，切换到手动模型输入，不显示为成功。
- **No recommendation**：保留发现结果，要求用户手动选择，不自动固定模型。
- **Partial failure**：列出已完成和未完成阶段；保留可恢复草稿，禁止显示“已完成”。
- **Save failed**：说明正式配置是否未应用，以及是否存在已写入的凭据或草稿；提供明确重试入口。
- **Success**：重新读取 workspace，展示已保存 Provider、模型和生效状态。

离开未保存快速配置时使用现有离开保护；非敏感输入可以保留在当前 React 会话，API Key 不进入 localStorage、React Query cache 或项目记忆。

## 12. 凭据安全

- API Key 使用密码输入，不回显旧值。
- API Key 不进入 URL、日志、错误消息、runtime scene、测试 fixture 或浏览器持久缓存。
- 自动检测请求只发送到本地 Vibelution API；UI 不直接向 Provider 发送请求。
- 日志只记录 Provider ID、阶段、结果、错误类型、耗时和模型数量。
- 凭据写入仍由现有用户环境变量路径拥有。

## 13. 可访问性和视觉规则

- 所有输入拥有可见标签和稳定错误关联。
- 自动阶段使用文字和图标，不只依赖颜色。
- 焦点顺序为服务商、API Key、高级区、检测按钮、结果候选、确认按钮。
- busy、disabled、error、warning 和 success 状态不得改变按钮尺寸或主要布局。
- 按钮贴合内容；只有“检测并生成配置”和“确认并保存”使用明确主操作强调。
- Provider 模板使用选择器或紧凑选择面，不再展示大面积模板按钮墙。

## 14. 测试和验证

### 14.1 自动测试

- 纯逻辑：模板到 draft 的映射、端点和协议补全、稳定推荐规则、无候选、身份不伪造。
- 组件契约：首屏只有两个条件必填项，高级参数默认收起，管理面与快速配置不同时渲染。
- 状态契约：检测中、认证失败、发现降级、无推荐、保存失败和成功。
- 安全契约：API Key 不出现在渲染文本、持久 cache、日志 payload 或错误摘要。
- 路由契约：确认前不调用配置应用；确认后使用现有 draft 与 apply 路径并刷新 workspace。
- 保留 Provider 管理现有模型引用、取消固定、凭据替换和诊断保护测试。

### 14.2 构建和视觉验证

- 运行相关 Vitest 与 `npm --prefix web run build`。
- Launcher 刷新后检查 `/config`。
- 浅色和深色分别检查 1280×720、1600×900、1920×1080。
- 检查 idle、checking、auth error、discovery fallback、preview、saving、success 和最长中英文标签。
- 确认无页面级横向溢出、无底部操作条遮挡、无加载跳动和应用 console error。

## 15. 模式、日志和发布判断

- Logging：受影响。复用配置服务的有界审计，并补充 quick-setup 阶段状态；不得记录凭据或完整 Provider 响应。
- Developer/formal mode：parity preserved。两种模式共享同一配置契约；现有 `structuredActionsDisabled` 和 Launcher 控制规则继续生效。
- Runtime refresh：用户测试前 required。
- Project memory：实现合入本地 main 后同步 `web-workbench-surface` lane。
- Version impact：patch。

## 16. 验收标准

- 设置页默认信息层级明确，用户能在首屏识别当前配置状态和下一步。
- 快速配置首屏只要求服务商和 API Key 两个条件必填项。
- 标准 Provider 从输入到配置预览只需一次主操作，从预览到正式保存只需一次确认。
- Provider 列表、详情和向导不再同时纵向堆叠。
- 自动检测结果可解释，失败、降级和部分状态不伪装为成功。
- 正式配置只在用户确认后应用，且继续使用外部 operator config 作为唯一事实源。
- API Key 不泄漏到日志、界面、缓存、测试或项目记忆。
- 三个桌面视口和双主题通过真实浏览器验收。
