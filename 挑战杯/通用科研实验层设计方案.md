# 通用科研实验层设计方案

状态：实施合同（schema v2 设计基线）
更新时间：2026-07-16
适用范围：Vibelution 通用科研团队、主页实验阶段卡片、挑战杯 XH-202619 参赛实例

## 1. 设计结论

Vibelution 只维护一套通用科研团队。领域、课题和实验方法都是任务配置，不通过复制团队或硬编码 Agent 角色实现。

主页中间实验卡片使用四层合同：

```text
researchMode
  -> experimentPurpose
  -> experimentMethod
  -> ExperimentAdapter
```

- `researchMode` 决定当前科研闭环覆盖 A 假设/计划、B 实验/反馈，或 A+B 完整闭环。
- `experimentPurpose` 决定为什么做实验、什么结论可以回答问题。
- `experimentMethod` 决定需要哪些输入、计划字段、指标和证据。
- `ExperimentAdapter` 决定由哪个真实执行能力完成 prepare/smoke/full run/result collection。

Agent 可以推荐前三层，但用户保存后的选择是当前计划的事实源。Adapter 由系统按方法、能力、环境和配置确定性选择，不能由 LLM 猜测可执行器 ID。

## 2. 非目标

- 不为每种实验方式创建一支新团队。
- 不把预测编码、FashionMNIST 或神经科学字段写进通用合同。
- 不把“深度资料审查”“论文结论复核”当作实验方法；它们属于证据阶段。
- 不把“环境探针”当作实验方法；它是所有可执行方法的 preflight 能力。
- 不把 smoke/proxy 结果包装成正式实验结果。
- 不允许前端选择状态成为独立事实源。

## 3. 四层合同

### 3.1 ResearchMode

```text
hypothesis_and_plan   # 赛题方向 A：假设生成与研究计划设计
experiment_feedback  # 赛题方向 B：实验任务规划与反馈迭代
full_research_loop   # A+B 完整闭环，挑战杯默认
```

约束：

- `hypothesis_and_plan` 可以输出可执行研究计划，但不声称实验已运行。
- `experiment_feedback` 必须绑定已有研究问题、假设或明确目标。
- `full_research_loop` 必须保留“证据 -> 假设 -> 计划 -> 结果 -> 下一轮计划”的版本关系。

### 3.2 ExperimentPurpose

每个计划有一个 `primaryPurpose`，可有多个 `secondaryPurposes`：

```text
feasibility          # 是否可运行、是否值得进入正式实验
baseline_comparison  # 与公平基线比较
falsification        # 主动寻找反驳条件
ablation             # 分离组件或机制贡献
replication          # 按来源协议复现
robustness           # 分布、参数、seed、场景稳健性
```

`successCriteria`、`failureCriteria` 和 `inconclusiveCriteria` 必须由 purpose 约束，禁止只有一个“passed”布尔值而无法解释科学含义。

### 3.3 ExperimentMethod

首批方法枚举：

```text
model_training_inference
dataset_analysis_benchmark
numerical_simulation
statistical_causal_test
theoretical_symbolic_validation
external_instrument_experiment
```

方法定义的是输入和证据合同，不等同于执行环境。例如 `numerical_simulation` 可以由本地 Python、远程 API 或外部仿真平台 Adapter 执行。

| 方法 | 必填专属配置 | 必备正式证据 |
|---|---|---|
| 模型训练/推理 | dataset、model、baseline、metrics、seed、budget | 配置、数据快照、日志、指标、artifact |
| 数据分析/基准 | sources、schema、transform、split、metrics | 来源、版本、清洗记录、输出表、指标 |
| 数值仿真 | simulator、scenario、parameters、sweep、replicates | 环境、参数、轨迹/结果、汇总统计 |
| 统计/因果检验 | H0/H1、sample、test、alpha、effect、confounders | 样本、检验输出、效应量、不确定性 |
| 理论/公式验证 | assumptions、derivation、boundary、counterexample | 推导、符号检查、适用边界、反例 |
| 仪器/外部实验 | protocol、instrument、sampling、approval、operator | 协议、采集记录、校准、审批、结果文件 |

### 3.4 ExperimentAdapter

Adapter 注册记录：

```json
{
  "adapterId": "builtin.pytorch_supervised_experiment",
  "adapterVersion": "1.0.0",
  "method": "model_training_inference",
  "executionMode": "local_process",
  "capabilities": ["validate", "prepare", "smoke", "full_run", "collect", "cancel"],
  "availability": "available",
  "unavailableReason": "",
  "requirements": {
    "runtime": ["python", "pytorch"],
    "network": false,
    "accelerator": "optional"
  },
  "priority": 100
}
```

统一接口语义：

```text
describe()       -> AdapterDescriptor
canHandle(plan)  -> CapabilityDecision
validate(plan)   -> ValidationReport
prepare(plan)    -> PreparedExperiment
smoke(prepared)  -> ExperimentRunResult
fullRun(prepared)-> ExperimentRunResult
collect(runRef)  -> ExperimentRunResult
cancel(runRef)   -> CancelResult
resume(runRef)   -> ExperimentRunResult  # 可选能力
```

选择规则：

1. `method` 必须完全匹配。
2. Adapter 必须满足计划声明的 capability 和 execution constraints。
3. 过滤 `unavailable/disabled`。
4. 用户显式选择且可用时优先；否则按项目配置 priority 确定性选择。
5. 无可用 Adapter 时保留该方法选项，但返回 `unavailableReason`，不得静默退化到人工成功。

## 4. ExperimentPlan schema v2

正式 JSON Schema：`schemas/research_experiment_method.schema.json`。迁移期间，schema v2 合同以现有 plan envelope 的 `experimentContract` 字段保存；旧 `experimentPlan` 只是前端迁移完成前的只读派生投影，不是第二事实源。

核心结构：

```json
{
  "schemaVersion": 2,
  "planId": "exp-plan-...",
  "revision": 1,
  "teamId": "research-team",
  "researchProfileId": "challenge-cup-predictive-coding",
  "researchMode": "full_research_loop",
  "purpose": {
    "primaryPurpose": "baseline_comparison",
    "secondaryPurposes": ["ablation", "robustness"]
  },
  "experimentMethod": "model_training_inference",
  "adapterSelection": {
    "requestedAdapterId": "",
    "resolvedAdapterId": "builtin.pytorch_supervised_experiment",
    "resolvedAdapterVersion": "1.0.0",
    "selectionSource": "system_priority"
  },
  "researchQuestion": "...",
  "hypothesisRefs": ["hypothesis-..."],
  "evidenceRefs": ["paper-note-...", "review-..."],
  "methodConfig": {},
  "metricContract": {},
  "decisionContract": {},
  "artifactContract": {},
  "reproducibilityContract": {},
  "iterationContract": {},
  "status": "draft"
}
```

### 4.1 统一结果信封

所有 Adapter 输出相同的事实信封：

```text
runId / planId / planRevision
method / adapterId / adapterVersion / executionMode
inputSnapshotHash / configHash / seeds
startedAt / completedAt / durationMs
status: prepared | running | completed | failed | cancelled | partial
metrics[] / artifacts[] / logRefs[]
conclusion: support | refute | inconclusive
conclusionRationale / uncertainty / boundaryConditions
feedbackSignals[]
nextPlanProposal
```

`completed` 只表示执行完成；科学结论仍必须是 `support/refute/inconclusive` 之一。执行失败不得映射成 `refute`。

### 4.2 版本与切换

- 没有 run 的 `draft`：可以修改方法，服务端保存各方法的独立草稿。
- 已有 smoke/full run：切换方法会创建 `revision + 1`，写 `supersedesPlanId`，历史计划不可原地改写。
- `running`：锁定方法切换；必须等待完成或显式取消。
- 切换回旧方法：恢复该方法最近的 draft，而不是把另一方法字段强行映射过来。
- Agent 推荐写入 `recommendation`；用户最终保存写入 `experimentMethod`。推荐不能覆盖已保存选择。

## 5. 状态机

```text
draft
  -> validating
  -> needs_input | adapter_unavailable | ready_for_prepare
  -> prepared
  -> smoke_running
  -> smoke_review
  -> ready_for_full_run | needs_revision | rejected
  -> full_run_running
  -> result_review
  -> iteration_proposed
  -> superseded | archived
```

关键门禁：

- `ready_for_prepare`：方法字段完整，Adapter 可用，preflight 通过。
- `ready_for_full_run`：smoke 只证明链路和基本行为可运行，不证明科研结论。
- `iteration_proposed`：必须存在结果结论、反馈信号和下一轮计划差异。
- 正式知识入库：仍经过 Evidence Review、Knowledge Steward 和 Ingestion Approval Gate。

## 6. 主页实验卡片合同

### 6.1 信息结构

```text
实验阶段 / 当前轮次 / 状态
[A 假设与计划] [B 实验与反馈] [A+B 完整闭环]

实验目的：主要目的 + 次要目的
实验方法：[模型] [数据] [仿真] [统计] [理论] [外部实验]
Agent 推荐：方法、理由、置信度、缺失条件

动态方法表单
Adapter：可用状态、执行方式、依赖、preflight
成功/失败/不确定标准
上轮反馈 -> 本轮变化

[保存草稿] [运行 Smoke] [开始正式实验]
```

### 6.2 交互要求

- 选项栏使用 segmented control 或 tabs；窄屏折叠为 select，不横向溢出。
- 方法不可用时显示但 disabled，并直接展示原因。
- 切换方法时布局主体保持稳定，不让卡片高度瞬时塌陷；使用字段 skeleton 或预留最小高度。
- 离开未保存草稿前给出明确提示；已保存的各方法草稿可恢复。
- 运行状态、停止原因、当前 Adapter 和轮次始终可见。
- 用户覆盖 Agent 推荐后显示“用户选择”，不继续展示为“自动推荐已采用”。
- 所有选择键盘可达，有可见 focus，状态不只依靠颜色表达。

## 7. 事实源与兼容迁移

| 事实 | Canonical source | Writer | Readers / derived surfaces | 刷新规则 | 旧事实处理 |
|---|---|---|---|---|---|
| 实验计划与版本 | 现有 `experiment_plans/index.json` 的 schema v2 record | experiment planning service | TeamsRoute、Agent tools、交付导出 | mutation 后按 team query invalidation | v1 只读迁移一次 |
| 方法目录 | 后端 ExperimentMethod registry | registry owner | API、主页选项栏、Agent planner | 服务启动/配置变化 | 替换散落模板常量 |
| Adapter 能力与可用性 | Adapter registry + preflight result | adapter registry | router、主页状态 | preflight/运行环境变化 | 不由前端推测 |
| 用户最终选择 | schema v2 active plan/draft | 用户通过 API | Agent、router、UI | 保存成功后刷新 | 不由 localStorage 覆盖 |
| Agent 推荐 | active plan recommendation | planning Agent | 用户、审查记录 | 新证据或用户请求重新推荐 | 与最终选择分离 |
| 运行结果 | ExperimentRunResult ledger | Adapter/result collector | review、iteration、knowledge ingestion | run event 更新 | 人工登记标记 external/manual |

迁移约束：

1. v1 `dataset/metric/baseline/smokePlan` 仅由 migration reader 映射到 `model_training_inference.methodConfig`。
2. 首次成功保存后只写 schema v2；不长期双写。
3. 迁移记录保留 `migratedFromSchemaVersion=1` 和时间，不改变已有 run 事实。
4. v1 读取兼容层在所有存量记录迁移并通过回归测试后删除。

## 8. 挑战杯预测编码首个验收案例

该案例只是 `researchProfile`，不能进入通用枚举。

### 8.1 配置

```text
researchProfileId: challenge-cup-predictive-coding
researchMode: full_research_loop
primaryPurpose: baseline_comparison
secondaryPurposes: [ablation, robustness]
experimentMethod: model_training_inference
dataset: FashionMNIST（固定版本、split、checksum、license/source）
baseline: 相同训练预算下的标准 backprop 模型
candidate: 预测编码启发的局部/迭代推理候选
ablation: 移除关键预测误差反馈或迭代推理组件
seeds: 至少 3 个固定 seed
```

建议指标：

- 主指标：分类 accuracy 或与任务一致的核心指标。
- 机制指标：reconstruction/prediction error。
- 训练指标：收敛轮次、稳定性、seed 方差。
- 成本指标：wall time、峰值内存、参数量或等价计算预算。

### 8.2 公平性门禁

- baseline 与 candidate 使用相同数据版本、split、seed 集和预算。
- 超参数搜索预算和停止规则显式记录。
- 不用 synthetic smoke proxy 作为正式结果。
- 负结果和 `inconclusive` 可以进入迭代，不能为了参赛叙事改写成成功。
- 所有关键科学解释回指 evidence/claim；实验结果只支持其实际测到的范围。

### 8.3 端到端验收

1. 上游问题、证据和可证伪假设能够生成 schema v2 计划。
2. 主页默认显示 Agent 推荐的“模型训练/推理”，用户可切换并恢复草稿。
3. Adapter preflight 明确数据、依赖、设备和可运行状态。
4. smoke 生成日志和 artifactHash，只开放 full run 门禁。
5. full run 真实执行 baseline/candidate/ablation，产生可复现结果。
6. Review 给出 `support/refute/inconclusive`，并列出边界和不确定性。
7. 根据反馈生成 revision 2，页面显示相对 revision 1 的计划差异和原因。
8. 导出内容覆盖 Problem Statement、Rationale、Technical Details、Datasets、Methods、Experiments、Results 和 References。
9. 保存脱敏 Qwen/百炼调用证据，不记录 API Key 或完整 prompt。

## 9. 实施顺序

### Task 1：合同与迁移门禁

- Backend：schema v2 validator、method registry、v1 migration reader。
- Frontend：共享 TypeScript DTO，不继续在 `TeamsRoute.tsx` 内复制大段局部类型。
- 验证：每种 method 一条合法 fixture；缺字段、未知枚举和错误迁移必须失败。

### Task 2：Adapter registry 与结果信封

- 把现有 smoke runner 包装为受限 smoke Adapter，不改变 proxy 边界。
- 新增 deterministic routing 和 availability/preflight API。
- 验证：可用、不可用、用户 override、无匹配 Adapter、运行失败不误判科研结论。

### Task 3：主页动态卡片

- 在现有实验计划账本上改造，不另建平行页面。
- 实现三层选择 UI、动态方法表单、Adapter 状态、草稿恢复和版本切换保护。
- 验证：桌面/窄屏、键盘、loading/disabled/error/running、切换不丢数据。

### Task 4：预测编码真实 Adapter 与闭环

- 把真实 FashionMNIST 实验包装为模型实验 Adapter。
- 输出统一结果信封，生成 revision 2 反馈计划。
- 验证：至少三 seed、baseline/candidate/ablation、公平预算、复现命令和结果差异。

### Task 5：赛题交付映射

- 把计划、结果、证据链、迭代差异和 Qwen/百炼证据映射到 PDF/演示/API。
- 验证：代表性案例可在 10 分钟内完整演示，技术方案不超过 20 页。

## 10. 成功标准

- 团队不因实验方式切换而重建或换角色。
- 方法目录来自后端事实源，前端没有硬编码第二套枚举。
- 切换实验方式会替换方法配置和 Adapter，但保留研究问题、证据、假设和版本链。
- 至少一个真实 Adapter 完成“计划 -> 运行 -> 数据 -> 分析 -> 下一轮计划”。
- smoke、正式实验、人工登记和不可用状态不会混淆。
- 预测编码案例可以证明通用合同，但通用合同不依赖预测编码字段。
