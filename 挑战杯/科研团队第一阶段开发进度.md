# 挑战杯科研团队第一阶段开发进度

更新时间：2026-07-04 23:15:37 +08:00

适用范围：Vibelution `ai科学研究团队` 的挑战杯科研流程，重点是第一阶段 `知识搜集`。本文用于下一轮开发规划，不是用户操作手册。

## 1. 当前结论

当前第一阶段已经从旧的多节点流程收敛为四个用户可理解步骤：

1. 搜索资料
2. 资料提炼
3. 资料审查
4. 资料入库

其中：

- `搜索资料` 已经具备可运行链路：创建批次、生成搜索计划、分配查询、执行 metadata-only 搜索、写入 DataRecord、导入 source_manifest 候选。
- `资料提炼` 已经具备后端提炼账本链路：阶段任务可回写 `candidateExtractions[]` / `recordExtractions[]`，并沉淀到 `metadata.contentExtraction.evidenceLedger`。
- `资料审查` 已经具备 Agent 批处理链路：资料质量评估 Agent 可批量审查候选资料，也支持 force 重新审查。
- `资料入库` 已经具备一键链路：复用资料审查、候选关系图、入库包、Team Knowledge source/proposal/review 门禁，最终可写入正式 KnowledgeItem。
- 下一轮最高优先级缺口不再是“后端是否能提炼”，而是把 Evidence Ledger 展示到资料卡、资料提炼详情和资料关系整理入口，让用户能看见每条 claim 的来源锚点和缺证据状态。

项目 HTML 与代码目前已同步，`挑战杯/research_team_flow_design.html` 已包含 `M6.69 资料提炼 Evidence Ledger`。

### 3.2 搜索资料

已完成：

- 用户可启动知识搜集批次。
- 系统生成 `DataSearchPlan/querySeeds`。
- 系统创建通用 `DataProcessingRun`。
- 系统创建 `CollectionAssignment`，把查询分配给功能 Agent。
- 支持无 key 多源 metadata 搜索，优先使用 OpenAlex、arXiv、SearXNG、DDGS 等公开来源，并在写入 DataRecord 前过滤低相关、域名不匹配或明显噪声结果。
- 搜索结果写入 DataRecord。
- DataRecord 会自动导入 source_manifest 候选。
- 支持“搜索下一批”。
- 支持 activeWorkRun 显示后台搜索状态。
- 搜索过程事件进入对话式过程流。
- 搜索结果和搜索过程分离展示。
- 搜索结果可按来源类型过滤。
- 结果卡显示 DOI、网页、本地路径或缺少来源。
- 机器 API/公开索引证据被放入搜索证据区域，而不是直接把索引 JSON 当成用户正文。

边界：

- 当前搜索是 metadata-only，不下载全文 PDF。
- 不写正式 Team Knowledge。
- 不写 RAG。
- 不写正式知识图谱。

剩余问题：

- 重复搜索会产生重复 DataRecord；虽然候选导入可以幂等，但原始资料记录数量会膨胀。
- DataRecord 与 source_manifest 的数量关系仍需要更清晰的统一投影，否则用户容易看到“已搜索 40，但页面只显示 8”之类的错觉。
- 搜索过程还没有完全复用对话 UI 的成熟消息组件，当前更像服务事件时间线。

### 3.3 资料提炼

当前状态：

- 已有 source_manifest 候选库。
- 已有 DataRecord -> source_manifest 的导入桥。
- 已有 `knowledge-collection/extract` 后端切片，可幂等把本轮 DataRecord 同步为 source_manifest 候选。
- 已有阶段任务结构化回写切片，可把资料提炼 Agent 的 `candidateExtractions[]` / `recordExtractions[]` 写入 `metadata.contentExtraction.evidenceLedger`。
- Evidence Ledger 会保留 `claims`、`keyFindings`、`citations`、`sourceRefs`、`evidenceRefs`、`limitations`、`uncertainty`、`riskFlags`、`supportLevel` 和 `nextAction`。
- 每条 Evidence Ledger 记录会标记 `evidence_ready` 或 `missing_evidence_anchor`；缺 `sourceRef` / `page` / `citation` / `evidenceRef` 锚点时，候选回写会降级为 `needs_review`。
- 前端有“资料提炼结果”页面，可展示本轮候选资料。
- 资料提炼页面能避免把原始 DataRecord 与候选资料混在一起。

真实缺口：

- Evidence Ledger 仍主要停在 CandidateStore metadata；资料卡和资料提炼详情尚未把 evidence_ready / missing_evidence_anchor 显示成用户可读状态。
- 资料关系整理尚未优先使用 Evidence Ledger 来解释图谱边来自哪条 claim、哪条 citation 或哪页原文。
- Agent 私聊任务已经能结构化回写，但前端还缺“本轮提炼证据账本”的一级入口和筛选视图。

建议下一步：

- 前端读取 `metadata.contentExtraction.evidenceLedger`。
- 资料卡显示 evidence_ready / missing_evidence_anchor 数量。
- 资料提炼详情新增 Evidence Ledger 列表，展示 claim、keyFinding、citation/sourceRef/page/evidenceRef、supportLevel、riskFlags 和 nextAction。
- 资料关系整理优先展示 evidence_ready 的 claim，并把 missing_evidence_anchor 作为补证据 action。
- 前端：
  - 资料提炼卡保留 Agent 主按钮。
  - 已无待提炼记录时显示 `查看提炼结果` 或 `重新提炼`。
  - 右侧详情显示 Evidence Ledger 覆盖率和缺锚点清单。

## 5. 当前主要风险

### 5.1 四步用户模型与旧代码模型不完全一致

用户看到的是：

1. 搜索资料
2. 资料提炼
3. 资料审查
4. 资料入库

代码里仍残留：

- collection
- candidate
- screening
- graph
- memory

风险：

- 后续开发容易把“候选图”和“入库包”重新做成用户步骤。
- 统计口径分散，导致顶部卡片和底部列表不一致。
- 资料提炼没有独立 API 时，用户会觉得第二步是空的或只是查看页。

### 5.2 统计口径未统一

目前常见统计来源：

- DataProcessingRun records
- CollectionAssignment queries
- CandidateStore source_manifest
- sourceQualityStatus
- candidateGraph summary
- knowledgeIngestionStatus
- 前端当前筛选/分页列表

风险：

- 顶部显示 `通过 31`，底部当前页只显示 6 条。
- 用户无法区分“总数、当前页、当前过滤条件、本轮候选、正式入库”。

建议：

- 增加统一投影：`KnowledgeCollectionStageProjection`
- 每个阶段只从一个 projection 读：
  - total
  - filtered
  - page
  - pending
  - completed
  - failed
  - nextAction

### 5.3 Agent 过程仍不够像对话链路

已经有过程页，但它更像 workflow event 时间线。

用户需要的是：

- 哪个 Agent 在什么时候做了什么。
- 输入是什么。
- 输出是什么。
- 写到哪里。
- 下一步交给谁。
- 失败时为什么失败。

建议：

- 复用对话消息组件或建立兼容 `ConversationTimelineMessage` 的投影。
- 搜索结果和 Agent 过程继续保持两个子页：
  - 结果：只看资料。
  - 过程：只看 Agent 执行流水。

### 5.4 搜索结果来源仍需加强可溯源

已做 DOI/网页/本地文件区分，但还需要稳定规则：

- DOI：显示 DOI 和 `https://doi.org/...`
- 网页：显示页面标题和来源 URL
- 本地 PDF：显示本地路径、sha256、页码
- 数据集：显示 dataset id 或下载页
- API 证据：默认折叠为“搜索证据”
- 无来源：显式标红或标黄，不能混入正常资料

### 5.5 搜索噪声与去重不足

目前 repeated search 会造成：

- DataRecord 变多。
- 候选导入可能因幂等不重复，但用户仍看到原始资料列表有重复。
- 候选图可能出现重复节点或低价值关系。

建议：

- 增加 DOI/sourceRef/title 归一化去重。
- 搜索资料结果默认展示“去重后的资料”，高级模式再看原始 DataRecord。
- 候选图只使用通过审查且去重后的候选。

## 6. 下一步建议开发顺序

### M6.56：统一四步阶段投影

目标：

- 后端提供或前端集中计算一个统一 projection。
- 解决顶部卡片、底部列表、右侧详情数量不一致。

建议输出：

- `stageId`
- `label`
- `status`
- `inputCount`

目标：

- 让“资料提炼”变成真实可执行阶段，而不是只查看候选库。

建议实现：

  - `data_processing_service.list_records`

目标：

- 每个阶段都能展示“像对话一样”的执行过程。

建议：

  - messageId
  - stageId
  - agentName
  - agentRole
  - modelName
  - action
  - inputSummary
  - outputSummary
  - artifactRefs

验收：

### M6.59：资料卡溯源统一

目标：

- 每个资料卡都能清楚回答“这是什么、来自哪里、能不能打开”。

建议：

- 建立统一 `SourceCardViewModel`。
- 来源类型：
  - DOI
  - paper_url
  - pdf_file
  - dataset
  - local_file
  - api_evidence
  - missing_source

验收：

- 点击卡片不会默认打开公开索引 JSON。
- 主按钮优先打开 DOI、论文网页或本地文件。
- API 原始搜索结果只在“搜索证据”里看。

### M6.60：资料入库状态四层化

目标：

- 明确第一阶段最终到底入了哪里。

建议 UI 显示四层状态：

1. 团队知识库 KnowledgeItem
2. 团队共享记忆
3. RAG
4. 正式知识图谱

验收：

- 资料入库完成后，用户知道哪些已完成，哪些仍在治理边界外。
- 不再把 CandidateStore、KnowledgeItem、RAG、official graph 混称为“入库”。

### M6.69：资料提炼 Evidence Ledger

目标：

- 让资料提炼 Agent 的结构化输出不只停留在会话摘要里，而是成为可审查、可回溯、可用于 paper_note 和候选关系整理的证据账本。

已实现：

- `source_collection_stage_writeback_tool` 接收 `candidateExtractions[]` / `recordExtractions[]`。
- 写回 `metadata.contentExtraction.evidenceLedger`。
- 保留 `claims`、`keyFindings`、`citations`、`sourceRefs`、`evidenceRefs`、`limitations`、`uncertainty`、`riskFlags`、`supportLevel` 和 `nextAction`。
- 统计 `evidenceLedgerCandidateCount`、`evidenceReadyCandidateCount`、`missingEvidenceAnchorCount`。
- 结构化内容缺 citation/page/source/evidence 锚点时进入 `missing_evidence_anchor`，并使候选状态降级为 `needs_review`。

待接：

- Teams 资料卡和资料提炼详情展示 Evidence Ledger。
- 资料关系整理用 Evidence Ledger 标注候选边的证据来源。
